# Git ブランチ・コミットメッセージ・プルリクエスト規約

本リポジトリでは、日本の開発現場で広く推奨されているベストプラクティスを採用します。
エージェントがブランチ名・コミットメッセージ・プルリクエスト文面を提案する際は、**複数の候補を並べず、最も適切な「1種類のみ」を提案**してください。

---

## 1. ブランチとコミットの粒度原則

- **1ブランチ ＝ 1要件ファイル** (`docs/requirements/REQ-XXX-<slug>.md`)
  - 1つのブランチ（＝1つのプルリクエスト）は、単一の明確な目的・関心事を持つ規模に保つ。
  - 複数の独立した機能や大きすぎる要件は、事前に要件ファイルを複数に分割し、別ブランチとして実施する。
- **1コミット ＝ 要件ファイル内の1タスク**
  - 要件ファイル内に定義された1つのタスクが完了するごとに1回コミットする。
  - コミットメッセージ単体を読むだけで、そのままプルリクエストの説明文として転用できるレベルの情報量（Why / What / Impact）を必ず記載する。

---

## 2. ブランチ名の命名ルール

### フォーマット
```text
<prefix>/<short-description>
```
（GitHub Issue 等と紐づく場合は `<prefix>/issue-<番号>-<short-description>`）

### ルール詳細
- **提案数**: 必ず **1種類のみ** 提案する。
- **文字種**: 半角英数字・小文字・ハイフン区切り（`kebab-case`）。
- **長さ**: `<short-description>` は英語 3〜5 単語程度で、変更内容が一目でわかる簡潔な表現にする。
- **プレフィックス (`<prefix>`) の定義**:
  - `feature/` : 新機能の追加・要件の実装（例: `feature/escl-scanner-discovery`）
  - `fix/` : バグ・不具合の修正（例: `fix/brother-capabilities-xml-parse`）
  - `hotfix/` : リリース後の緊急バグ修正
  - `refactor/` : 外部仕様を変えない内部設計改善・リファクタリング（例: `refactor/scan-job-session-handler`）
  - `docs/` : ドキュメント・要件定義のみの作成や更新（例: `docs/define-initial-requirements`）
  - `test/` : テストコードの追加・修正（例: `test/escl-status-parser`）
  - `chore/` : ビルド設定、開発環境、CI/CD、依存パッケージ等の整備（例: `chore/setup-antigravity-rules`）
  - `perf/` : パフォーマンス・メモリ効率の改善

---

## 3. コミットメッセージのルール

Conventional Commits をベースとし、**「コミットメッセージだけでプルリクエストの内容も記載できるレベル」** とするため、1行目の件名（Subject）だけでなく、空行を挟んだ本文（Body: 背景・目的 / 変更内容 / 影響範囲・備考）を必須とします。

### フォーマット（必ず1種類のみ提案）
```text
<type>(<scope>): <変更の要約（日本語・50文字目安・末尾に句点「。」をつけない）>

## 背景・目的
<なぜこの変更が必要なのか、解決する課題や対応する要件タスクの背景を記載>

## 変更内容
- <具体的に何を変更・追加・削除したかを箇条書きで記載>
- <主要なモジュール・クラス・関数・設定などの変更点>

## 影響範囲・備考
- <影響を受ける機能・OS（macOS / Windows）・対象機器（Brother / 汎用eSCL）など>
- <破壊的変更の有無、動作確認の観点、または特記事項>
```

### `<type>` の定義
- `feat`: 新しい機能や要件タスクの実装
- `fix`: バグや不具合の修正
- `docs`: ドキュメントや要件定義のみの変更
- `style`: コードの動作に影響しない変更（フォーマット、空白、セミコロン等）
- `refactor`: 機能追加やバグ修正を伴わない内部構造のリファクタリング
- `perf`: パフォーマンスを向上させる変更
- `test`: テストの追加や既存テストの修正
- `chore`: ビルドプロセス、設定ファイル、開発ツール、依存パッケージ等の変更

### `<scope>` の定義
変更対象の領域を英語小文字で指定します（プロジェクト全体にわたる場合は省略可）。
- 例: `escl`, `discovery`, `brother`, `macos`, `windows`, `ui`, `scan`, `config`, `docs`, `agent`

## 4. プルリクエスト（PR）のルール

プルリクエストを作成する際は、対象ブランチの要件ファイルおよび各コミットメッセージの内容を集約し、[`.github/pull_request_template.md`](../../.github/pull_request_template.md) に準拠した **タイトル（1種類）** と **本文（1種類）** を作成します。

### PR タイトルのフォーマット
```text
<type>(<scope>): <ブランチ全体の変更要約（日本語・50文字目安）>
```

### PR 本文の構成セクション
1. `## 概要`（対応する要件ファイル、関連Issue、このPRの結論サマリー）
2. `## 背景・目的`（各コミットの「背景・目的」を統合した変更理由）
3. `## 変更内容`（各コミットの「変更内容」を整理した実装項目一覧）
4. `## 影響範囲`（対象OS［macOS / Windows］、対象機器［Brother / 汎用eSCL］、既存機能への影響）
5. `## 動作確認・テスト`（チェックリスト形式での確認項目。特に最優先の「Brother × macOS」での確認観点を含む）
6. `## レビュアーへの特記事項・補足`（重点レビュー箇所、別ブランチへ切り出したスコープ外事項など）

---

## 5. チャット画面への出力・表示ルール

- **ファイル出力内容の再掲禁止**:
  - 要件ファイルやドキュメント、コードなど、**ファイルとして出力した内容を改めてチャット画面に表示・要約して説明する必要はありません**（作成したファイルのリンクのみ提示してください）。
- **チャット画面に必ず表示するもの**:
  - 以下の Git 関連の提案内容は、ユーザーがそのままコピー＆ペーストして使用できるよう、**必ずチャット画面に直接表示**してください：
    1. **提案するブランチ名（1種類）**
    2. **提案するコミットメッセージ（1種類）**（※要件をタスク分解した際は、分解して作成した要件ファイル自体をコミットするためのブランチ名・コミットメッセージも必ずチャット画面で提案すること）
    3. **提案するプルリクエストのタイトルと本文（1種類）**
